## Motivation and disposition of Experiment 1

`prereg/v5-synthesis.md`'s Experiment 1 (the "planted-reduct scaling"
benchmark, `benchmarks.py`'s `run_scaling_experiment`) scales the
*candidate-property count* `n` (10 to 100) while deliberately holding
the *reachable-set size fixed at `k + 1 = 6` tuples regardless of `n`*
-- registered that way on purpose, so `n = 100` stayed tractable, and it
answered the question it was built for (does the SAT/MaxSAT encoding
scale in the number of variables). It does not, and was never
registered to, answer a different question: does the engine scale as
the *reachable set itself* grows, and does it still work correctly when
more than one minimal hitting set exists (Experiment 1's own planted
reduct is unique by construction).

This document registers that different benchmark. Experiment 1's own
result stays frozen, cited, and is not retroactively edited: once this
benchmark's real results are committed, it is relabelled
`exploratory_v5_0` in `benchmarks.py`'s own output and in NOVELTY.md,
kept for its own (still valid) question, and superseded as *the*
primary scaling claim by what is registered below -- the same
disposition this project already gave `out/results/authority_bench.json`
(`exploratory_v6_0`) when v6.1 superseded it.

## The multi-reduct scaling family (registered construction, hand-derived and proved below)

Two boolean "twin" properties, `twin_a` and `twin_b`, plus `q` boolean
"noise" properties `noise_1 .. noise_q`, each ranging over `R = 10`
values (`0..9`), for `q` in `{3, 4, 5}` (three registered family sizes).

**Reachable set** (exactly `1 + R^q` tuples, by construction, not
sampled):
- One tuple `T_0`: `twin_a = 1, twin_b = 1`, every noise property at its
  baseline value `0`.
- For every one of the `R^q` possible noise assignments `c` (including
  the baseline `c = 0`): one tuple `(twin_a = 0, twin_b = 0, noise = c)`.

This gives `1 + 1000 = 1001` (`q=3`, exceeds 10^3), `1 + 10000 = 10001`
(`q=4`, exceeds 10^4), and `1 + 100000 = 100001` (`q=5`, exceeds 10^5)
reachable tuples -- the three registered sizes, each a clean `10^q + 1`,
comfortably at or above its target threshold by construction, not by
measurement after the fact.

**Verdict** (the single registered predicate, `benchmarks.py`'s own
established style of naming a synthetic predicate without a "loss"
reading -- `run_scaling_experiment`'s `"all_signal_properties_set"` is
the direct precedent): `twin_both_set(t) = (t.twin_a == 1) and
(t.twin_b == 1)`.

**Hand-derivation, checked here before any code exists (Registration
discipline: not adjusted afterward to match a measured result):**

- `T_0` is the only tuple with `twin_a = 1`; every other tuple has
  `twin_a = 0`. Symmetrically for `twin_b`. So the partition of the
  reachable set by `{twin_a}` alone is exactly `{T_0}` (verdict True,
  trivially uniform, one element) and "everything else" (verdict False
  for all of them, since `twin_a = 0` forces the verdict False
  regardless of `twin_b`/noise) -- both cells uniform, so **`{twin_a}`
  is sufficient (Definition 4)**. The identical argument, symmetrically,
  shows **`{twin_b}` is sufficient**.
- **The empty set is not sufficient**: `T_0` (verdict True) and any bulk
  tuple (verdict False) agree on the empty set (vacuously, as any two
  tuples do) yet disagree in verdict.
- Since `{}` is insufficient and both singletons are sufficient, **both
  `{twin_a}` and `{twin_b}` are minimal -- two distinct reducts of
  cardinality 1 each.** This is the registered "planted structure
  yielding multiple minimal hitting sets": exactly two, verified by hand
  above, not asserted.
- **The core is empty**: a property is in the core iff some reachable
  pair differs ONLY in that property (Definition 1). No reachable tuple
  has `twin_a = 0, twin_b = 1` or `twin_a = 1, twin_b = 0` -- the only
  `twin_a = 1` tuple is `T_0` itself (`twin_b = 1` there too), and every
  `twin_b = 1` tuple is likewise only `T_0`. So no pair differing ONLY in
  `twin_a` (or ONLY in `twin_b`) exists in the reachable set at all;
  neither property is individually witnessed. Empty-or-partial core with
  multiple reducts is exactly Negative Proposition N's own abstract
  shape (`appendix-a-proofs.md`), occurring here by explicit
  construction rather than discovered as a surprise.
- **Every noise property is correctly excluded from every reduct**:
  fixing `twin_a = twin_b = 0` (the "bulk" partition), two bulk tuples
  differing only in some `noise_j` always agree in verdict (both False)
  -- no discernibility contribution. And `{noise properties alone}` is
  NOT sufficient: the bulk tuple with `noise = 0` (the baseline
  assignment) shares its full noise vector with `T_0`, yet the two
  disagree in verdict -- projecting onto noise alone conflates them.
- **`build_discernibility_family`'s cost is linear in the reachable
  set, not quadratic**: only one tuple (`T_0`) carries the True verdict,
  so the pairwise cross-verdict loop is `1 x R^q`, not `R^q x R^q` --
  tractable at `R^q = 100,000` (Milestone D5's own `benchmarks.py`
  comment already flags the quadratic case, over v1's/v2's real
  reachable sets, as the reason `make benchmarks` is not wired into
  `release-check`; this construction is deliberately shaped to avoid
  that cost, not merely tolerate it).
- **`remove_redundant_supersets`'s output has exactly one set,
  `{twin_a, twin_b}`, at every `q`**: every cross-verdict pair is `T_0`
  vs. some bulk tuple `(twin_a=0, twin_b=0, noise=c)`; the difference
  set is always `{twin_a, twin_b}` unioned with whichever noise
  properties happen to differ from `T_0`'s baseline (a strict superset
  of `{twin_a, twin_b}` whenever `c != 0`, and exactly `{twin_a,
  twin_b}` when `c = 0`, the bulk tuple sharing `T_0`'s own baseline
  noise). Every other difference set is therefore a proper superset of
  `{twin_a, twin_b}` and is absorbed. **Predicted family size after
  superset removal: exactly 1, at every `q`** -- a specific, falsifiable
  number, not a vague "small," registered before Phase D5.1 runs it.
- **Exhaustive cross-check is feasible at every registered size**: total
  candidate properties `n = 2 + q` is `5, 6, 7` -- `2^n` is `32, 64, 128`
  subsets, trivially exhaustible via `reduct.exact_reducts()` regardless
  of how large the reachable set itself grows (`q` inflates the
  reachable set via its DOMAIN size, `R^q`, not via more candidate
  properties). Registered to run at all three sizes, not only the
  smallest -- unlike Experiment 1, where only `n = 10` was exhaustible.

**Declared per-property costs** (for the weighted-MaxSAT backend, `D2`'s
third backend): `cost(twin_a) = 1.0`, `cost(twin_b) = 2.0`, every noise
property `cost = 0.1`. `{twin_a}` and `{twin_b}` tie on cardinality
(both 1) but not on cost (1.0 vs. 2.0) -- registered so minimum-cost
synthesis has a genuine, predicted, single correct answer
(`{twin_a}`) distinguishable from minimum-cardinality synthesis's
two-way tie, on this family specifically (Experiment 2 of `prereg/
v5-synthesis.md` already tests cost-vs-cardinality divergence on a
different domain; this is a second, independent instance of the same
question, on a family built for a different primary purpose).

## Metrics (registered, four per backend, three backends, six families)

Three backends (`synthesis.py`, D2, unmodified): `find_any_sufficient_
contract` (SAT), `find_minimum_cardinality_contract` (cardinality
MaxSAT), `find_minimum_cost_contract` (weighted MaxSAT). Six families:
the three synthetic sizes (`q = 3, 4, 5`) plus v2, v4, and
data-and-communications.

- **Discernibility family size after superset removal**:
  `len(remove_redundant_supersets(build_discernibility_family(...)))`
  -- computed once per family (not per backend, since it does not
  depend on which backend consumes it), reported alongside each
  family's per-backend rows.
- **Exact**: does the backend's returned contract match the
  known-correct answer -- the two-reduct set (`{twin_a}` or `{twin_b}`,
  either is a valid "exact" cardinality/SAT answer; `{twin_a}`
  specifically for the cost backend) for the synthetic families, and
  the already-committed core/reduct facts for the three real domains --
  cross-checked against `reduct.exact_reducts()` directly (feasible at
  every registered size, per the hand-derivation above), not merely
  asserted.
- **Wall time**: `time.perf_counter()` around the backend call alone,
  `benchmarks.py`'s own established pattern.
- **Peak memory**: `resource.getrusage(resource.RUSAGE_SELF).ru_maxrss`
  delta around the same call, same established pattern.

No pass/fail hypothesis is registered for wall time or memory
themselves (descriptive, as in Experiment 1) -- **exact** is the scored
metric, expected to hold at every family and every backend given the
hand-derivation above; any failure is a real, reportable finding (an
engine bug, or an error in this registration's own proof), not smoothed
over. Two-sided: this registration does not assume the SAT ("any
sufficient") backend returns a MINIMAL contract on the synthetic
families (it is only asked for sufficiency, not minimality, by
`synthesis.py`'s own contract) -- its "exact" check is scored against
sufficiency and the specific known-correct minimal answers only where
`find_any_sufficient_contract` happens to already return one of them;
where it returns a larger, merely-sufficient set instead, that is
reported as such, not as a failure of the benchmark.
